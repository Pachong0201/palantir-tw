# 台湾开源情报平台 · 设计文档（v0.1 草案）

> 仿 Palantir Gotham 的分析范式：**本体驱动融合 + 断言级证据分级 + 人在回路**。
> 团队内部平台，Windows 常驻机部署。MVP 域：选举与政治。

## 1. 核心原则

- **一切结论都是断言（Assertion）**：图谱里没有"裸事实"，每条关系都带证据等级、来源文档、有效时间，可回溯到原始材料。这是 Palantir 区别于普通舆情工具的根本。
- **证据分级（沿用 ogasawara 框架 A–E）**：A 官方原始件 / B 官方转述或多源交叉 / C 单一可靠媒体 / D 社媒单一来源 / E 未证实线索。机器给建议等级，人可调整。
- **人在回路**：实体消解低置信度的进人工审核队列；研判结论由人写，系统供证。
- **多域共本**：选举与政治是 MVP 域，新闻舆情、两岸动态后续作为新数据源 + 新断言类型接入同一本体，不另建系统。

## 2. 分层架构

```
┌─ 采集层    RSS / 爬虫 / API / 手工导入  →  raw_items（原样存档+hash去重）
├─ 抽取层    DeepSeek 结构化抽取 → 实体候选 + 断言候选（附建议证据级）
├─ 消解层    规则匹配 + LLM 仲裁 → 图谱；低置信 → 人工审核队列
├─ 本体层    Postgres + pgvector（实体/断言/文档/金流）
├─ 分析层    实体360°视图 / 关联图 / 时间线 / 地图 / 金流 / 异常检测
└─ 应用层    分析师工作台 Web UI / NL 查询 / 报告生成 / 飞书推送
```

## 3. 本体 Schema（MVP）

| 实体 | 说明 | 关键字段 |
|---|---|---|
| Person | 政治人物（候选人、民代、官员、幕僚、金主） | 姓名、别名、党籍、出生地、wiki_id |
| Party | 政党/派系 | 名称、派系谱系 |
| Organization | 公司、财团法人、协会、媒体 | 统一编号（商工登记）、负责人 |
| District | 行政区/选区 | 层级（县市/乡镇市区/选区/村里）、GeoJSON 边界 |
| Election | 选举场次 | 类型（九合一/总统立委/罢免/补选）、日期 |
| Candidacy | 参选记录（人×选举×选区×政党） | 得票、得票率、当选与否、竞争对手 |
| Event | 政治事件 | 类型（登记/造势/司法/争议/听证）、时间地点 |
| Transaction | 政治献金记录 | 捐赠者(人/组织)→专户、金额、日期、捐赠类型 |
| Document | 来源文档 | 出处、URL、等级、原文指纹 |
| Assertion | 断言（边） | subject→predicate→object、grade、doc、valid_from/to |

断言谓词示例：`参选于`、`隶属政党`、`亲属/配偶`、`幕僚/助理`、`捐赠`、`涉案`、`表态支持`、`经营/负责人`。

## 4. 数据源清单（台湾特有）

**结构化官方数据（优先级高，证据 A/B 级）**
- 中央选举委员会：开票结果、候选人登记资料、公投（2022/2024/2026）
- 监察院阳光主题网：政治献金专户收支、公职人员财产申报
- 经济部商工登记：公司/团体统一编号、负责人 → 金主企业背景
- 司法院裁判书查询：政治人物涉案记录
- 政府电子采购网：标案与得标商 → 政商网络线索
- 立法院公报：质询、议案、表决记录

**非结构化来源（证据 C/D 级，LLM 抽取）**
- 新闻 RSS：中央社、公视、联合、中时、自由、民视、上报、镜周刊等
- PTT（HatePolitics / Gossiping）、Dcard 政治板（注意反爬与合规）
- YouTube 公开频道数据、FB 公开页（API 受限，谨慎）
- 维基百科/Wikidata：人物基础资料、亲属关系（辅助消歧，不单独成证）

## 5. 管线设计

- **Ingest workers**：每源一个 adapter，APScheduler 定时跑；raw_items 原样入库（HTML/JSON + SHA256 指纹去重），先存后解析，重放成本为零。
- **Extract worker**：DeepSeek structured output，输出 `{entities, assertions, evidence_hint}`；Prompt 内置台湾政治实体词表与政党别名。
- **Resolve**：规则层先撞（姓名+选区+党籍上下文、统一编号精确匹配）；冲突/多义走 LLM 仲裁；仍不定 → `review_queue` 人工裁决，裁决结果回流为消解规则。
- **Assert**：断言入库即带 grade/doc/time；同一谓词多来源时保留多条断言并标注一致性（印证/冲突）。

## 6. 存储选型

- **Postgres 15 + pgvector**：实体/断言用关系表 + JSONB；向量做新闻相似度与消歧 embedding。
- 图谱查询用递归 CTE + 物化视图；不引入 Neo4j——Windows 单机运维单进程最省，实体规模（万级）远未到需要专用图库的门槛。
- 全文检索先用 Postgres FTS，够用再迁。

## 7. 分析层功能

- **实体 360° 页**：Person 页=职务履历+参选历史+关系图+金流+事件时间线+关联文档，一处看全（对标 Gotham Object View）。
- **Link chart**：Cytoscape.js 多跳扩展，按断言谓词/证据级过滤。
- **Timeline**：事件-文档-断言三轨时间线。
- **Map**：Leaflet + 台湾乡镇 GeoJSON，选举结果 choropleth、地缘分析。
- **金流视图**：献金榜单/桑基图、异常检测（大额集中、得标商关联）。
- **监测订阅**：实体/关键词订阅 → 飞书机器人推送。
- **NL 查询**：DeepSeek 把自然语言转成图谱查询，返回断言+证据链（不是裸答案）。

## 8. 技术栈

Python 3.11+ / FastAPI / SQLAlchemy / APScheduler / Postgres 15+pgvector / Jinja+HTMX+Cytoscape.js+Leaflet（轻依赖，不引入前端构建链）/ DeepSeek API（`DEEPSEEK_API_KEY`）。

## 9. 分期路线

| 阶段 | 内容 | 验收 |
|---|---|---|
| 0 | 脚手架 + CEC 历史选举数据导入 | 实体页/选区结果可查 |
| 1 | 政治献金 + 财产申报 + 人物关系 | link chart + 金流视图 |
| 2 | 新闻/社媒采集 + LLM 抽取 + 审核队列 | 断言自动入库、人审闭环 |
| 3 | NL 查询 + 公文式报告生成 + 飞书推送 | 一键出研判稿 |
| 4 | 扩域：全域舆情、两岸动态 | 新源接入本体 |

## 10. 风险与开放问题

- **政治献金数据可得性**：监察院公开查阅多为网页影像/PDF，可能需 OCR 或半人工补录——Phase 1 先抓可机器读的列表页，OCR 单独立项评估。
- **社媒抓取稳定性/合规**：FB API 收紧、Dcard 反爬；策略是官方结构化数据为主、社媒为辅，宁可少抓不违规。
- **实体消解准确率**：台湾政治人物同名常见（如同名议员、宗族名），人工审核队列是兜底，消解规则持续积累。
- **单机容量**：Windows 常驻机跑 Postgres + 采集 + API，数据量万级实体/百万级断言内无压力。
